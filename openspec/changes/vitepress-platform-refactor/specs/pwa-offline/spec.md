## ADDED Requirements

### Requirement: Platform is installable as a PWA with a web app manifest

The VitePress site SHALL include a Web App Manifest (`manifest.webmanifest`) generated by `vite-plugin-pwa`. The manifest SHALL declare at minimum: `name`, `short_name`, `theme_color`, `background_color`, `display: "standalone"`, and icon entries.

#### Scenario: Manifest is served at build time

- **WHEN** the site is built with `pnpm build`
- **THEN** a `manifest.webmanifest` file SHALL be present in the build output and linked in the HTML `<head>`

### Requirement: PWA service worker caches WASM runtimes with a CacheFirst strategy

The PWA service worker (generated by `vite-plugin-pwa` / Workbox) SHALL apply a `CacheFirst` runtime caching strategy for WASM runtime URLs matching the Pyodide CDN, php-wasm CDN, and the locally built WASM files (`/wasm/virtual-fs/`, `/wasm/asgi-bridge/`). Cached WASM responses SHALL have a maximum age of 30 days.

#### Scenario: WASM runtime is served from cache on repeat visits

- **WHEN** a user has visited at least one challenge page previously and the browser has cached the WASM runtime
- **THEN** subsequent page loads SHALL serve the WASM runtime from cache without a network request

### Requirement: PWA service worker applies NetworkFirst to HTML and StaleWhileRevalidate to other assets

The PWA service worker SHALL apply `NetworkFirst` to navigation requests (HTML pages) and `StaleWhileRevalidate` to static assets (JS, CSS, images, fonts). This ensures content stays current while maintaining fast load times from cache.

#### Scenario: HTML pages prefer network

- **WHEN** the user navigates to a challenge list page while online
- **THEN** the service worker SHALL attempt a network fetch first and fall back to cache on failure

#### Scenario: Static assets load from cache while revalidating in background

- **WHEN** the user loads a page with cached JS/CSS
- **THEN** the cached version SHALL be served immediately and the network response SHALL update the cache in the background

### Requirement: PWA service worker does not conflict with the challenge routing service worker

The PWA service worker SHALL be registered separately from the challenge routing service worker (`challenge-sw.js`). The challenge routing service worker intercepts requests to `challenge-*.localhost` origins; the PWA service worker SHALL NOT intercept those requests. The `challenge-sw.js` file SHALL be excluded from the PWA precache manifest.

#### Scenario: Challenge requests are not intercepted by PWA SW

- **WHEN** a challenge panel sends a request to `http://challenge-sqli.localhost/`
- **THEN** only the challenge routing service worker SHALL handle that request; the PWA service worker SHALL NOT intercept it

#### Scenario: challenge-sw.js is excluded from PWA precache

- **WHEN** the PWA service worker is installed
- **THEN** `challenge-sw.js` SHALL NOT appear in the precache manifest
